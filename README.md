# AR光の柱 修正サンプル

スマートフォンのカメラ映像に、向きセンサー（DeviceOrientation）で 3D の「光の柱」を重ねる Web AR のサンプルです。
学生作品 [chisasuma42-del/ar-pillar](https://github.com/chisasuma42-del/ar-pillar) の `index.html` の座標計算を見直し、修正したものです。

**デモ：<https://fumiakim.github.io/ar-pillar-sample/>**（スマートフォンで開いてください）

- 開始ボタンを押した時に向いていた方向が「正面」になります（右90°・左90°にも柱があります）
- 「ここを正面にする」で正面を取り直せます
- 実景と柱が回転時にずれて“滑る”場合は「画角」スライダーで合わせます（値は端末に保存されます）
- PC など向きセンサーが無い環境では、ドラッグで見回せます（動作確認用）

> iPhone ではカメラ・モーションセンサーとも HTTPS が必須です。GitHub Pages ならそのまま動きます。

## 元コードの問題点

行番号は元の [`index.html`](https://github.com/chisasuma42-del/ar-pillar/blob/main/index.html) のものです。

### 1. 図形が逆方向に動く：コンパス値を α にそのまま代入している（158–160行）

```js
if (event.webkitCompassHeading) {
    alpha = event.webkitCompassHeading;
}
```

| 値 | 増える向き（上から見て） |
|---|---|
| `event.alpha`（W3C） | **反時計回り** |
| `event.webkitCompassHeading`（iOS） | **時計回り**（北=0, 東=90） |

回転方向が逆なので、iPhone で右を向くと CG の世界も右へ回ってしまい、柱が本来と逆方向へ流れます。
three.js（r128）で計算して確認した結果：

```
右へ30°向いた時、正しい α(=330°)を使った場合 → カメラ前方 ( 0.50, 0, -0.87)  … 右を向いている
コンパス値30°を α に入れた場合               → カメラ前方 (-0.50, 0, -0.87)  … 左を向いてしまう
```

### 2. 位置が突然跳ぶ：α・β・γ の組を崩している（同上）＋ ジンバルロック

α・β・γ は Z→X'→Y'' 順のオイラー角で、**3つで1つの回転**を表します。
スマホを立てて構える AR の姿勢は β ≈ 90°で、ちょうどこのオイラー角の特異点（ジンバルロック）です。
この付近では、わずかな傾きで

```
(α, β, γ) = (20°, 95°, 10°)  →  (200°, 85°, -170°)
```

のように表現が切り替わります（どちらも**同じ姿勢**）。ブラウザは α・β・γ を一緒に切り替えるので、3つを揃えて使えば問題ありません。
しかし α だけコンパス値（切り替わらない）に差し替えると、β・γ だけが反転し、**計算上の姿勢が 180° 跳びます**（上の例で誤差 180.0° を確認）。
立てた持ち方で少し前後に傾けた時に柱が突然別の場所へ移動するのはこれが原因です。

**修正**：α・β・γ はセンサーの値を組のまま使い、コンパス値は姿勢計算に混ぜない。
「正面」は開始時（またはボタン押下時）のカメラの水平方向から求め、水平回転のオフセットとして掛けます（`recenter()`）。

### 3. センサー値が null の時に 0 として使っている（154–156行）

```js
let alpha = event.alpha || 0;
```

起動直後や未キャリブレーション時は `null` が来ることがあり、その瞬間だけ α=0 の向きへ跳びます。
`null` の時はイベントを捨てるようにしました。（`|| 0` は値が `0` の時にも働く点にも注意）

### 4. CG が映像より遅れて“泳ぐ”：フレーム依存のスムージング（190行）

```js
camera.quaternion.slerp(targetQuaternion, 0.15);
```

毎フレーム 15% だけ近づける方式は、60fps で約 0.1 秒、30fps ではその倍遅れます。
カメラ映像は遅れないので、首を振るたびに柱が実景に対して遅れてから追いつきます。
時間ベース（`1 - exp(-dt/τ)`、τ = 0.04 秒）にし、遅れを小さくしました。

### 5. 画角が実際のカメラ映像と合っていない（110行・9行）

`PerspectiveCamera(60, …)` の 60° は固定値ですが、画面に映るカメラ映像の画角は

- 端末のカメラ（iPhone 1x で長辺約 65°）
- `object-fit: cover` による切り抜き（縦長画面では左右が切られる）

で決まります。合っていないと、回転した時に実景の上を柱が滑るように動きます。
映像の解像度と画面サイズから「画面に見えている範囲の角度」を計算するようにしました（`updateProjection()`）。
機種差はスライダーで調整できます。

### 6. 映像と CG の表示領域がずれる（9–10行）

映像は `100vh`、WebGL は `window.innerHeight` で大きさを決めていますが、iOS Safari ではアドレスバー分この2つが一致しません。
映像と canvas を同じ `position: fixed; inset: 0` の箱に入れ、その実寸で描画するようにしました。

### 7. iPad の横持ちで上下と左右が入れ替わる（169行）

```js
const orient = window.orientation ? THREE.MathUtils.degToRad(window.orientation) : 0;
```

センサーの α・β・γ は「端末本体（縦持ちが基準）」の向きなので、横持ちで画面が回っている時は画面の回転角で補正する必要があります。
この角度を 0 と誤ると、カメラの「上」が水平方向を向いた状態（90°ロール）になり、**左右に振ると柱が上下に動き、上下に傾けると左右に動きます**。

- iPad の Safari は既定で「Mac 用サイト」として振る舞うため `window.orientation` が存在せず、上のコードでは常に 0 になる
- Safari では `window.orientation` と `screen.orientation.angle` の符号が逆になる報告もある（[WebKit Bug 254863](https://bugs.webkit.org/show_bug.cgi?id=254863)）

修正版では、iPhone / iPad では API を使わず、**表示が縦長か横長か**と**重力が端末のどちら側に向いているか**から画面の回転角を求めています（`updateScreenAngle()`）。
左側面が下なら +90°、右側面が下なら −90°。それ以外の端末では `screen.orientation.angle` を使います。

### その他

- `facingMode: { exact: "environment" }` は PC 等で失敗するため `ideal` に
- 柱の回転速度を時間ベースに

## 発展：北（実際の方角）に合わせたい場合

実際の方位に柱を立てたい場合も、**α を差し替えるのではなく**、
「センサー姿勢から求めたカメラの水平方向」と「コンパス方位」の差を水平オフセットとして求め、`yawOffset` に入れるのが正しい方法です。
Android Chrome なら `deviceorientationabsolute` イベントの α が北基準なので、そのまま使えます。
